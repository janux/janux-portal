# Client build migration: gulp/webpack 3 → Vite

Branch: `dev-vite-build`. The client's gulp 3.9.1 + webpack 3 +
karma/jasmine/PhantomJS stack has been replaced with Vite 7 +
`@vitejs/plugin-vue2` + Vitest. `client/gulpfile.js`, `client/gulp/`,
`client/build/`, `.babelrc`, `.bowerrc`, `client/vendor/` (dead — see
below) and `client/test/karma.conf.js` are gone; `client/index.html`
(Vite's required real entry file) replaces `client/src/index.pug`.

This document records why each non-obvious change was necessary, for
whoever next touches the build and hits something that looks like the same
shape of problem. See `CLAUDE.md` for the current, supported way to build
and run the app.

## Why Vue and Vue-Material had to move too

`@vitejs/plugin-vue2` peers on `vue: ^2.7.0-0`, so the build-tool swap
forced a real Vue 2.5.2 → 2.7.16 bump, which in turn forced Vue-Material
beta-7 → beta-16 (peers on `vue: ^2.7.14`). Root-cause TypeScript 5 / Vue 3
was **not** in scope: Vue-Material has no Vue 3 release and all 31 SFCs use
`md-*` components, so that migration is a separate UI-library swap, not a
build-tool swap.

## Things that had to change to make Vite (Rollup) happy

Webpack was more lenient about all of these; useful context if a new build
error shows the same shape.

- **`resolve.extensions` needs `.vue` added explicitly** — Vite's default
  list doesn't include it, unlike webpack's; a few imports (e.g.
  `./login-component`) omit the extension.
- **`resolve.preserveSymlinks: true` is required.** `janux-people` /
  `janux-authorize` are `file:../server/vendor/...` symlinks pointing
  outside `node_modules`. Without this, Rollup resolves them to their
  realpath, which no longer matches `commonjsOptions`'s default
  `/node_modules/` include pattern, and their named CJS exports (`Person`,
  `PhoneNumber`, etc.) go undetected — surfaces as `"X" is not exported by
  ".../janux-people.js/index.js"`.
- **Webpack's `~pkg/path` convention for LESS `@import`/`url()` is not
  honored by Vite's Less integration** — unlike Vite's Sass handling, the
  leading `~` is not stripped; it had to be removed from the source
  (`bootstrap.less`, `font-awesome.less`, `main.less`, `login.less`,
  `drag-and-drop.less`) for these to resolve as bare node_modules/alias
  specifiers. `<img src="~Img/...">` inside `.vue` templates is a different
  code path (the Vue SFC compiler's asset-url transform) and was left as-is.
- **Less 4's `math: 'parens-division'` default** makes a bare `/` between
  two plain numbers inert instead of doing division (avoids ambiguity with
  CSS shorthand like `font: 16px/1.5`). `mixin.less`'s `.rem()` mixin used
  bare division and needed explicit parens: `unit((@font-pixel-size /
  @conv-factor), rem)`.
- **`src/css/util.less` imported `icon/entypo/entypo`, which has never
  existed as a LESS source in this repo** (only a raw
  `vendor/entypo/css/entypo.css`) — dead since before this migration, but
  any LESS compiler, old or new, fails hard on a missing `@import`. Disabled
  rather than fabricated; restoring entypo icons is separate, unstarted
  work. `client/vendor/` (which only ever backed this one dead import) was
  removed along with it.
- `drag-and-drop.less` referenced `/img/drag_handle.png` as an absolute
  path, one directory prefix off from where the old build actually served
  copied images (`/static/img/...`) — probably already broken. Pointed at
  the `Img` alias instead, consistent with the other two image references
  in this codebase.
- `app.js` switched from `template: '<App/>'` (runtime template
  compilation) to `render: h => h(App)`, which is required to use Vue's
  runtime-only build — Vue 2's package.json already points `module` at
  `dist/vue.runtime.esm.js`, so no explicit `vue$` alias is needed once
  nothing compiles a template string at runtime.

## Left as-is, not fixed by this migration

- `test/common/security/**` (5 spec files) are pre-existing AngularJS specs
  (`module()`, `inject()`, `$httpBackend`) left over from the
  `janux-auth-seed` predecessor of this Vue app. They test code that no
  longer exists this way and were never runnable under karma either —
  `angular-mocks` was never a listed dependency. Excluded from the Vitest
  run rather than ported; rewriting them for the current Vue code is
  separate, unstarted work.
- `eslint.config.js` (flat config) surfaces real, pre-existing issues the
  old `eslint 4` + `plugin:vue/essential` setup never caught, including a
  few genuine `vue/no-mutating-props` bugs (mutating a prop object directly
  in `address.vue`, `email.vue`, `phone.vue`). Left as findings, not fixed
  here — that's app-code review, not a build-tool change.

## Verification performed

`vite build` (production bundle), `vite` (dev server, HMR client + module
transforms serving 200s), `vitest run` (1/1 passing, proves the alias +
jsdom wiring), and `eslint src test` (runs clean, reports the pre-existing
issues above) all run end-to-end against the real vendor symlinks.
